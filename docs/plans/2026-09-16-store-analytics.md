## 背景の確定事実（推測ではない）

- `scripts/release/store-status.mjs` は Play Developer Reporting API で `crashRate` と `distinctUsers` を取得済み。本セッションで再実行して動作を確認した
- 同 API はクラッシュ／ANR 系しか返さない。**インストール数・全ユーザー数・検索キーワードは対象外**（`store-status.mjs` のコメントに明記）
- Google 認証は `scripts/release/lib/play-api.mjs` の `getAccessToken(scope)` が任意スコープを受ける。追加依存ゼロ
- Apple 認証は `scripts/release/lib/asc-api.mjs` の `ascToken()` / `ascGet()` がそのまま使える
- リポジトリに `analytics/` は無く、ストア指標を Markdown へ書き出すスクリプトも無い
- `@google-cloud/bigquery` / `googleapis` は未導入

## 指標の 4 群と方針

| 群  | 指標                                              | 手段                                     | 本票での扱い                 |
| --- | ------------------------------------------------- | ---------------------------------------- | ---------------------------- |
| A   | クラッシュ率・ANR 率ほか Vitals                   | Play Developer Reporting API（実証済み） | **やる**                     |
| B   | ASC のインプレッション・コンバージョン率・初回 DL | App Store Connect Analytics Reports API  | **やる**（下記の但し書き）   |
| B'  | Play のリーチ・獲得・検索キーワード               | Play Console の BigQuery エクスポート    | **有効化状況の確認までやる** |
| C   | Apple Ads Basic のキャンペーン別内訳              | Apple Search Ads API                     | **やらない**                 |

C を切る根拠: だいどこ側の先行調査で Basic プランは ASC の UI でも内訳がグレーアウトし取得不可と判明済み。Advanced へ切り替えない限り自動化しても得るものが無い。

## 受け入れ基準

- [ ] `node scripts/release/store-analytics.mjs` を実行すると `analytics/<実行日>/summary.md` が生成され、A 群の表（日付・クラッシュ率・ANR 率・distinctUsers）が入っている
- [ ] 同コマンドに `--days 30` を渡すと、集計期間が 30 日の表になる（既定は 7 日）
- [ ] Play Developer Reporting API がデータ鮮度を超える `endTime` を要求されたとき、400 で落ちずに鮮度日まで自動で切り詰める
- [ ] 対象の GCP プロジェクトで Reporting API が無効なとき、例外で停止せず「有効化する URL」を含む行を summary.md に残して続行する
- [ ] `node scripts/release/store-analytics.mjs --check-bigquery` を実行すると、BigQuery エクスポートが「有効／無効／このサービスアカウントに閲覧権限が無い」のいずれかを、ブラウザを開かずに判定して表示する
- [ ] ASC Analytics のレポート要求が未作成のとき、既定では**作成せず**「`--create-asc-request` を付けると作成する」と表示して終わる
- [ ] `--create-asc-request` を付けたときだけ ASC にレポート要求を作成し、作成した要求の id を表示する
- [ ] ASC のレポートが取得可能なとき、ソースタイプ別のインプレッション・製品ページ閲覧数・初回ダウンロード数の表が summary.md に入る
- [ ] `pnpm test:scripts` が緑。新規 lib の純粋関数（行の畳み込み・TSV 解析・Markdown 生成・鮮度の切り詰め）に、壊れた入力を与えて落ちることを確かめるテストがある
- [ ] `analytics/` が `.gitignore` に入っているか、入れない判断の理由が票に書かれている
- [ ] 生成物・ログ・例外文言のいずれにも、サービスアカウントのメールアドレス・鍵・アクセストークン・署名付き URL が出ない

## スコープ外

- Apple Search Ads（C 群）の自動化。上記の根拠により着手しない
- 取得した数字の**解釈**（「なぜ落ちたか」の分析やアクションの提案）。本票は取得と整形まで
- ダッシュボード化・グラフ描画・時系列 DB への蓄積。出力は Markdown 1 枚
- だいどこ側への同じ仕組みの移植。さいえん手帳で動いてから別途判断する
- 定期実行（cron / GitHub Actions）の配線。手で叩く運用から始める
- Play Console / App Store Connect のブラウザ操作全般（CLAUDE.md §5 で「必ず止める」対象）

## 未解決事項

- **Play Console の BigQuery エクスポートが有効かどうか未確認。** 有効化は Play Console のブラウザ操作なので代行しない。本票では「API から読める形で有効かを判定する」ところまでを実装し、無効だった場合の有効化は利用者へ回す
- **エクスポート先の GCP プロジェクトが不明。** サービスアカウント JSON の `project_id` を既定の探索先と仮置きし、`--bigquery-project` で上書きできるようにする（仮）
- **ASC Analytics Reports API のレポート要求は App Store Connect アカウントへの書き込みになる。** 作成後 24〜48 時間はデータが出ない仕様。既定では作成せずフラグ必須とし、最初の 1 回の作成は利用者の承認を得てから行う
- **サービスアカウント JSON のパスが 2 系統ある。** スクリプト側の既定は `C:/secure/play-service-account.json`、`eas.json` 側は `C:/secure/saien-techo-play-service-account.json`。同一の鍵の別名コピーか別のサービスアカウントかはコードからは判断できない。新スクリプトは前者（`PLAY_SERVICE_ACCOUNT_KEY` で上書き可）に揃える
- **`analytics/` をコミットするか否かが未決。** 数字自体は秘密ではないが、リポジトリは private であり、公開状態が変われば流入の実数が露出する。仮に `.gitignore` へ入れ、利用者の判断で外す
