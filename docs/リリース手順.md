## 4b. リリースの順序（**末尾に置かない**）

```
バンプ PR → develop
  → develop → main のリリース PR をマージ
  → main で vX.Y.Z タグを打って push        ← 提出より前
  → **タグから**ビルド（git checkout vX.Y.Z）  ← 「タグ = 成果物の元」を定義にする
  → 検証（§5・release-verify）→ 実機確認
  → 提出（承認ゲート）
```

**リリースに要る工程を末尾に置くと落ちる。** このリポジトリで実際に落ちた 2 件:

- **1.0.0 のとき main が 114 コミット遅れたまま放置された。** 提出も公開も 07-28 の
  main で行われ、main が動いたのは 08-22（1.1）が最初。「リリースしてから main へ
  マージ」という順序だったため
- **v1.0.0 / v1.1.0 のタグが打たれていなかった**（2026-08-27 に遡って付与）。
  手順が「公開されたらタグ」だったため。**v1.0.0 は遡っても正確に打てなかった** —
  Android(vc2) と iOS(build 4) で元 commit が違い、当時 main 上に指せる commit が無い

**却下・出し直しではタグを動かす**（`git tag -f` → `git push -f`）。
iOS 1.0 は実際に build 2 → 3 → 4 と出し直している。**出し直しは通常運転**として扱う。
バージョン番号ごと上げるなら新しいタグになるので動かす必要はない。

**リリースブランチ（`release/x.y.z`）は作らない。** 末尾のマージが main と develop の
2 本に増えるだけで、上の失敗パターンを増やす。月 1 回程度のリリース頻度では
develop の凍結で足りる。

```powershell
foreach ($line in $creds) { $k, $v = $line -split '=', 2; Set-Item -Path "env:$k" -Value $v }
$env:EXPO_PUBLIC_ADMOB_ENABLED = "true"
$env:EXPO_PUBLIC_ADMOB_APP_OPEN_UNIT_ID = "ca-app-pub-2633806931583277/3771122951"
$env:EXPO_PUBLIC_ADMOB_REWARDED_UNIT_ID = "ca-app-pub-2633806931583277/3132828705"
$env:EXPO_PUBLIC_ADMOB_BANNER_UNIT_ID = "ca-app-pub-2633806931583277/6932472912"

# 2) ビルド（生 gradlew は禁止 — フックが止める。app.json 変更時は --prebuild）
node scripts/agent/build-android.mjs --bundle

# 2b) 鮮度チェック — いま作った AAB が app.json の版か（古い成果物の検証を防ぐ。release-verify §0）

# 3) 提出（リリースノートは listing-ja.md の「## リリースノート」節。送信前に 2b を自動で再実行する）
node scripts/release/submit-play-release.mjs --dry-run
node scripts/release/submit-play-release.mjs            # production へ
```

- **新規（未公開）アプリは draft リリースしか作れない**（スクリプトの既定）。AAB を載せたら
  Console の「公開の概要」→「変更を審査に送信」で申告一式と一緒に審査へ出す
- 公開後のアップデートは `--completed` を付ける（commit 即審査キュー）

- `bundleRelease` は SAIEN*UPLOAD*\* 未設定だと**意図的に失敗**する（debug 署名の AAB を
  Play へ上げない安全弁。build.gradle 末尾のゲート）
- 署名レール（signingConfigs.release + bundleRelease ゲート）は config plugin
  `plugins/withSaienUploadSigning.js` が prebuild のたびに自動注入する（android/ は
  gitignore のため手パッチは残らない — プラグインが単一ソース）
- versionCode は初回 1。**更新のたびに app.json の android.versionCode を上げる**

### R8（難読化・最適化）— 2026-08-14 に有効化

`app.json` の `expo-build-properties` で `enableMinifyInReleaseBuilds` と
`enableShrinkResourcesInReleaseBuilds` を `true` にしてある。**`android/` は
gitignore なので gradle.properties を手で触らないこと** — prebuild が上書きする。

実測の効果（AAB 内・非圧縮）:

|                               | R8 無効  | R8 有効  | 差分         |
| ----------------------------- | -------- | -------- | ------------ |
| dex（ユーザーが DL する部分） | 36.43 MB | 17.60 MB | **-51.7%**   |
| so（ネイティブ）              | 64.76 MB | 64.76 MB | ±0（対象外） |
| AAB ファイル                  | 58.76 MB | 57.35 MB | -2.4%        |

> **AAB の見かけの縮みが小さいのは、マッピングが載るから。** R8 を有効にすると
> `BUNDLE-METADATA/com.android.tools.build.obfuscation/proguard.map`（約 51.5 MB）が
> AAB に自動同梱される。**これはユーザーには配信されない**（Play が端末別 APK を
> 作る際に除去し、クラッシュの難読化解除に使う）。
> **WBS 3.12d「ProGuard マッピングの添付」は、これで自動的に満たされる** —
> submit スクリプトの改修は不要。

**`keystore.properties` を使う手は勧めない。** build.gradle は env と
`android/keystore.properties` の両対応だが、後者には落とし穴が 2 つある（実測）:

- **Windows パスがそのままだと壊れる。** Java の `Properties.load()` が `\` を
  エスケープとして解釈し、`C:\secure\saien-upload.keystore` が
  `C:securesaien-upload.keystore` に潰れて `validateSigningRelease` で失敗する。
  書くならスラッシュ表記
- **置くと APK の署名まで変わる。** `assembleRelease` もアップロード鍵で署名される
  ようになり、debug 署名で実機に入れてあるアプリへ `adb install -r` できなくなる
  （`INSTALL_FAILED_UPDATE_INCOMPATIBLE`）。ローカル検証へ戻すときは削除する

上の §5 冒頭のとおり **`SAIEN_UPLOAD_*` を env に流し込む手順が正**。

> **iOS のビルドは EAS クラウド一択。手元の Mac でのローカルビルドは原理的に不可能**
> （2026-08-28 に実測で確定）。**試す前にここを読むこと。**
>
> Apple は **2026-04-28 以降、Xcode 26 + iOS 26 SDK** でビルドしたものしか
> App Store Connect へのアップロードを受け付けない
> （developer.apple.com/news/upcoming-requirements/）。
> 手元の Mac は **Xcode 16.4 / iOS 18.5 SDK** で 8 世代足りず、`eas build --local` で
> 作った `.ipa` は `SUBMISSION_SERVICE_IOS_SDK_VERSION_ERROR` で弾かれた
> （さいえん手帳 1.2.0 で実測）。
>
> **Xcode を上げることはできない。**
>
> ```
> MacBookPro16,3（13" 2020・2 ポート版・Intel Core i5-8257U）
>   → macOS Tahoe 26 の対象外        → macOS は 15.7.9 が上限
>     → Xcode 26 は arm64 単独ビルドしか存在しない
>       → iOS 26 SDK が手に入らない → 提出できる成果物を作れない
> ```
>
> **`xcodes list` の `[Universal]` 表示は嘘。** 実際に `xcodes install 26.3` すると
> Apple Silicon 専用ビルドが降ってきて、`lipo -archs` は `arm64` 単独、
> 起動しようとすると **`bad CPU type in executable`**（XcodesOrg/xcodes#456）。
> **30 分のダウンロードを溶かして確認した。同じことを繰り返さないこと。**
>
> **macOS を上げても解決しない。** Apple Silicon 機に買い替える以外に道はない。
> → **ビルドは EAS クラウドで回す。枠が尽きたら翌月 1 日のリセットを待つ。**
>
> **Mac が役に立たなくなったわけではない。** 掲載スクショの取得（§7-7）と
> シミュレータでの動作確認は **Xcode 16.4 のままで問題なく通る**
> （1.2.0 の iOS スクショ 10 枚はこれで撮った）。**できないのはビルドだけ。**

```powershell
cd C:\Projects\saien-techo\apps\mobile
pnpm exec eas build -p ios --profile production
pnpm exec eas submit -p ios --profile production --id <BUILD_ID> --non-interactive
# ↑はバイナリを上げるだけ。**審査には入らない**（1.1 で両アプリとも「アップロード止まり」だった）
```

- `submit-asc-version.mjs` の単一ソース: バージョン/ビルド番号 = `app.json`、
  What's New = `docs/store/app-store/listing-ja.md` §6 の `### v<version>`、接続情報 = `eas.json`。
  **審査中・公開済みのバージョンには触らない**（冪等）。

- **`eas submit` の「Something went wrong」は当てにならない。** だいどこでは
  失敗表示のままアップロードが成功していた（2026-08-13）。
  **必ず App Store Connect の TestFlight 画面で実物を確認する。**
  失敗と誤認して再実行すると、2 回目はビルド番号重複で本当に落ちる。
  詳細ログは `https://expo.dev/accounts/keisato848/projects/saien-techo/submissions/<id>`
  の「Upload to App Store Connect」を展開すると読める（CLI には出ない）
- **`ios.buildNumber` は同一バージョン内で一意かつ増加。** `android.versionCode` と
  揃える運用にしている（app.json）。上げ忘れると提出が弾かれる

### 7-7. Mac 側の作業（Windows では不可）

手順の詳細は `.claude/skills/ios-release`。

- シミュレータ動作確認: `pnpm --filter mobile exec expo run:ios`
- **重点的に見るのは Windows で検証できなかった描画** — セーフエリア、角丸、
  ジェスチャーバーとの干渉、横スクロール帯。Android では実機でしか出ない
  不具合を複数踏んでいる（WBS §T3）
- 掲載スクショの取得は macOS 必須だが、**取得後のアップロードは Windows からで良い**
  （`node scripts/release/update-asc-screenshots.mjs [--dry-run]`）
- **取得は無人化できない。** iOS 17+ は `simctl openurl` でカスタムスキームを開くと
  SpringBoard が「"さいえん手帳" で開きますか?」を出し、**誰かが「開く」を押すまで
  アプリが起動しない**。`simctl` に入力注入は無く、AppleScript のクリックは
  補助アクセス許可が要る。`capture-ios-screenshots.mjs` は撮る前に毎回
  「アプリが前面に出たか」を確認して待つ（2026-08-14 に**7 枚とも
  「ホーム画面＋確認ダイアログ」を撮って captured と報告した**事故があったため）
- Windows から Mac を使う場合は **SSH ＋ 画面共有（VNC）**。Visual Studio の
  「Pair to Mac」に相当する製品機能は Expo には無いが、必要なのは
  `xcrun simctl` を叩くことだけなので SSH で足りる。確認ダイアログを押すときだけ画面が要る
