## 背景

1.1（写真から記録 #148 / キーボード修正 #134 / 無料枠 #151）のリリース作業と、
その途中で入った機能追加（写真から栽培登録 #139・PR #152 / だいどこ #208）で
起きたことの記録。**指摘レビューではなく作業の振り返り**だが、
再発防止の宿題が複数出たので同じ場所に残す。

このセッションで踏んだ失敗は**2 つの型に収斂する**。個別の不注意ではなく
構造的な問題なので、型ごとに整理する。

---

## 型 A: 「見るべき信号」を見ていない検証

**実行したコマンドの成否だけを見て、結果物そのものを見なかった。**
どれも「成功したように見えるが、対象や経路が違う」形で現れた。

### A-1. ストア用スクショが 8 枚とも中身なしだった

- **状態**: done
- **重大度**: 中
- **何が起きたか**: 撮影スクリプトが 8 枚とも「captured」を出したが、
  中身は**ローディングのスピナー**だった。既定の待ち 7 秒では画面が出来上がらない。
- **調査**: summary のファイルサイズが 20KB 前後と不自然に小さかった。
  中身が出ていれば 100KB 前後〜1MB になる。実際に開いてスピナーを確認した。
- **判断**: 対応する。待ち時間を延ばすだけでは同じ罠を踏むので、
  **サイズという機械的な見分け方**を手順に残すことを主眼にする。
- **対応**: `0736f41`（既定待ち 12 秒・両スクリプトに判別法を明記）

### A-2. 古い AAB を検証し、本命のビルドは壊れていた

- **状態**: done
- **重大度**: 高
- **何が起きたか**: AAB ビルドの完了を「**ファイルの存在**」で待った。
  ところが 8/14 の古い AAB が残っており、監視が即座に成立。
  完了と誤認して **APK ビルドを同時に開始**し、2 つの Gradle が
  `merged_native_libs` を奪い合って `StripDebugSymbols` が失敗、
  **AAB ビルドは 33 分かけて FAILED**。
  そのうえ `release-verify`（16KB・権限・EXIF）を**旧 v1.0 の AAB に対して実行**し、
  「3 項目 PASS」と報告してしまった。
- **影響**: 提出前に気づいたので実害なし。気づかなければ
  **旧版の検証結果を根拠に 1.1 を提出**していた。
- **調査**: AAB の日付が 8/14、マニフェストの versionName が 1.0.0 だった。
  ビルドログ末尾は `BUILD FAILED in 33m 44s`。
- **判断**: 対応する。判定を**終了コード**へ変え、同時ビルドをやめる。
  加えて**検証の最初にバージョンを確認する**手順を自分の運用に組み込む
  （機械化は「改善 1」へ）。
- **対応**: 再ビルド後に検証をやり直し 3 項目 PASS。宿題は「改善 1」

### A-3. Wi-Fi 経由の adb で応答が戻らず、製品側を疑いかけた

- **状態**: done
- **重大度**: 低
- **何が起きたか**: Pixel の一括読み取りが 2 枚とも
  「時間内に応答がありませんでした」。**サーバーは 200 を 4〜6 秒で返していた**。
  原因は **USB が抜けて reverse トンネルが Wi-Fi 経由になった**こと。
  同じ 2 枚が USB 接続時には成功していた。
- **調査**: 成功時は USB と Wi-Fi の 2 トランスポートが接続されていた。
  失敗時は Wi-Fi のみ。サーバーログには 200 が残っていた。
- **判断**: 製品側は直さない（本番はアプリが Railway へ直接 HTTPS で、
  adb トンネルは介在しない）。**検証環境の制約**として記録に留める。
- **対応**: なし（記録のみ）。副産物として**エラー処理の実機確認**になった —
  1 枚失敗しても残りを止めず、下書きは編集可能なまま残り手入力で登録できた

### A-4. スクショ 8 枚目が Play に載らないところだった

- **状態**: done
- **重大度**: 中
- **何が起きたか**: `update-play-screenshots.mjs --dry-run` が
  **「plan (7 files)」**と出した。`08-harvest-reads.png` はディスクにもコミットにも
  あるのに、反映側の `ORDER` 配列に入っていなかった。
- **調査**: 撮る側（`SHOTS`）と載せる側（`ORDER`）で並び順が二重管理だった。
  8 枚目を追加したとき撮る側だけ直していた。**dry-run が「plan (7 files)」と表示**して発覚。
- **判断**: 対応する。今回は `ORDER` に追加して塞ぐが、
  **二重管理そのものの解消**は別途行う（「改善 4」）。
- **対応**: `ORDER` に追加＋二重管理である旨のコメント

> **型 A の共通対策**: 「コマンドが成功したか」ではなく
> **「結果物が期待どおりか」**を見る。具体的には
> ①終了コード ②成果物のバージョン ③サイズ・件数 ④dry-run。
> このセッションで**唯一未然に防げた A-4 は、dry-run があったケース**。

## 型 B: 同じ事実が 2 箇所以上にあり、片方だけ更新される

**二重管理。9 件見つかった。** 特に「文書が実装を追いかけていない」形が多い。

### B-1. プライバシーポリシーが写真送信を 1 機能ぶんしか説明していなかった

- **状態**: done
- **重大度**: 高
- **何が起きたか**: #148 は収穫写真を `/garden/harvest` へ送るのに、
  ポリシー §4 は「**AI 相談機能について**」で AI 相談だけを説明していた。
  §1 の列挙も「AI 機能を使ったとき」。
  しかも **#143 の決定で「写真の読み取り」は UI で AI と名乗らない**ため、
  **利用者はこのずれに気づく手段がない**。
- **なぜ残ったか**: `data-safety.md` 冒頭に
  「申告内容を変える変更を入れたら必ずこのファイルも直すこと」と書いてあるのに、
  **#148 のマージ時に更新が漏れた**。散文の規約は守られない。
- **調査**: ポリシー §4 の見出しと本文、§1 の列挙をすべて確認。
  `/garden/harvest` を呼ぶ実装（`harvest-read.service.ts`）と突き合わせて乖離を確定。
- **判断**: 対応する。**Play のフォームの回答自体は変わらない**
  （種類・目的・共有先が同じ）が、**説明がずれていることが問題**。
  リリースノートに無料枠の件を書かないという判断とは別問題として扱う。
- **対応**: `dd852d0`（§4 を 2 機能へ・data-safety.md も更新・**公開 gist 同期済み**）。
  宿題は「改善 2」

### B-9. 「release ビルドではローカル E2E できない」は誤り

- **重大度**: 中

  「未デプロイのサーバー相手に実機検証する」選択肢が**最初から潰れる**。
  実際 #139 は本番へ出す前にこの経路で検証できた。
- **対応**: `be04273`（実測日と根拠つきで訂正）

## 型 C: テストが誤りのほうを固定していた

### C-1. 「また明日」の誤文言をテストがアサートしていた

- **状態**: done
- **重大度**: 中
- **何が起きたか**: #151 で無料枠を生涯 1 回にした際、枠切れの案内が
  **広告を出せないだけのときにも「また明日お試しください」**と言っていた
  （無料ぶんは生涯 1 回なので明日も 0 のまま）。
  そして `広告が出せないときは動画ボタン自体を出さない` が
  **その誤った文言をアサート**していた。**951 件が緑だったのはこれが理由。**
- **重要な訂正**: 当初「本番でも再現する」と報告したが**誤り**。
  `AdMobRewardProvider.isAvailable()` は `UNIT_ID !== ''` を見るだけの**設定の検査**で、
  production は実 ID を持つので常に true。本番で `!canWatchAdForMore` に入るのは
  上限到達のときだけで、そこでは「また明日」は**正しい**。
  嘘になるのは **`preview` プロファイル**（Stub プロバイダ）やローカル検証ビルド。
- **対応**: 2 状態を出し分け、両方を固定する回帰を追加（`fcf6138`）。
  前者は 42d314c に対して落ちることを確認済み。
- **判断**: 対応する。文言の修正だけでなく、
  **2 状態それぞれを固定する回帰**を足して同じ取り違えを防ぐ。
- **対応**: `fcf6138`
- **教訓**: **緑のテストは「仕様どおり」を意味しない。「書いたとおり」を意味する。**
  文言を変えるときは、その文言をアサートしているテストが
  **正しい状態を固定しているか**を読み直す。

## 改善（宿題）

### 改善 1: 成果物の「鮮度」を機械で見張る

- **状態**: open
- **重大度**: 高
- **指摘**: A-2。`release-verify` は AAB を受け取って検証するが、
  **その AAB がいつのものか・どのバージョンかを見ない**。
- **調査**: 旧 AAB で 3 項目 PASS と誤報した実績あり。
- **判断**: 対応する（未着手）。
- **対応**: なし（宿題）
- **案**: `check-elf-align.py` と同じ層に
  **「AAB / APK の versionName・versionCode を表示し、`app.json` と一致しなければ落ちる」**
  チェックを足し、`release-verify` の手順 1 に置く。
  ビルド時刻が `app.json` の更新より古い場合も警告する。

### 改善 2: 「実装と申告の対応表」を機械で見張る

- **状態**: open
- **重大度**: 高
- **背景**: B-1。`data-safety.md` の「必ず直すこと」は散文で、守られなかった。
- **案**: 外部送信するエンドポイントの一覧（`API_V1` を叩く箇所）を抽出し、
  **`data-safety.md` / プライバシーポリシーに列挙された機能数と突き合わせる**
  テストを足す。数が合わなければ落とす。
  `KeyboardAvoider` カバレッジテストと同じ発想で、**散文の規約を機械に移す**。
- **判断**: 対応する（未着手）。B-1 は法務文書のずれで、散文の規約では防げないことが実証された。
- **対応**: なし（宿題）

### 改善 3: 「存在しないパスを指す参照」を検出する

- **状態**: open
- **重大度**: 中
- **背景**: B-2〜B-4。既存の `foreign-app-identifier` 検査は
  「だいどこの識別子」を探すが、**「このリポジトリに無いファイルを指す参照」は見ない**。
- **案**: `.claude/skills/**` と `docs/**` から
  `scripts/...` `apps/...` のようなリポジトリ相対パスを抽出し、
  **実在しなければ pre-commit で落とす**。
  `validate-claude-customizations.mjs` に足すのが自然。
- **判断**: 対応する（未着手）。個別修正では同種が再発する。
- **対応**: なし（宿題）

### 改善 4: スクショの並び順の二重管理をやめる

- **状態**: open
- **重大度**: 中
- **背景**: A-4。撮る側（`SHOTS`）と載せる側（`ORDER`）で二重管理。
- **案**: `ORDER` を廃し、**`SHOTS` の `file` を単一ソース**にする
  （`capture-store-screenshots.mjs` から export して読む）。
  iOS 側（`capture-ios-screenshots.mjs`）も同様。
- **判断**: 対応する（未着手）。A-4 は dry-run で拾えたが、二重管理そのものを消すほうが確実。
- **対応**: なし（宿題）

### 改善 5: CI の実行を絞る

- **状態**: open
- **重大度**: 低
- **背景**: 今日だけで docs のみの PR が何度も CI を回した。
  作業ツリーに `paths-ignore` と `concurrency` を足す変更が**別セッションから**現れた。
  内容は妥当。**私はコミットしていない**（他セッションの作業のため）。
- **判断**: 見送る（このセッションでは触らない）。**他セッションが着手中**で、
  勝手にコミットすると相手の作業を横取りする。内容自体は妥当なので、
  そちらのセッションで完了させるのが筋。
- **対応**: なし（意図的に未着手）

### 改善 6: 手順書の「実測で確かめていない主張」を洗う

- **状態**: open
- **重大度**: 中
- **背景**: B-9。「できない」と書かれていたことが**実際にはできた**。
  この種の記述は選択肢を潰すので害が大きい。
- **案**: 手順書の断定（「〜できない」「〜すると必ず〜」）に
  **実測日と根拠**を添える規約にする。根拠の無い断定は疑ってよい印にする。
