## 指摘

### 1. 作業ログのテーブル名を `work_logs` と誤記

- **状態**: done
- **重大度**: 高
- **影響**: 実装者がそのまま書くと存在しないテーブルを触る
- **指摘**: 検討文書 §3 の 1.3 行に「`work_logs` に種別追加」。実テーブルは `care_logs`（schema.ts:229）。
- **調査**: リポジトリ全体で `work_logs` の出現は当該文書の 1 箇所のみ。あわせて kind は CHECK 制約なしの TEXT で、種別 `check` の追加に DDL 変更が不要なことも判明（設計が軽くなる正の発見）。
- **判断**: 対応する。
- **対応**: `care_logs` に修正し、「DDL 変更不要」を追記。

### 2. `photos` の列数を 7 と誤記（実際は 8）

- **状態**: done
- **重大度**: 低
- **指摘**: §6-1 の「photos は 7 列で撮影日時を持たない」。実際は `created_at` を含む 8 列。
- **調査**: 「EXIF の撮影日時が無い」という主張の本体は正しい（`created_at` は保存時の `nowIso()` で、ギャラリー選択では撮影時刻と一致しない）。
- **判断**: 対応する。列数を直し、`created_at` の性質を注記。

### 3. 「兆候あり → AI 相談へ写真つき」の導線を既存で足りると言い過ぎ

- **状態**: done
- **重大度**: 中
- **影響**: 1.3 の見積もりに効く
- **指摘**: エンドポイントと入力仕様（写真+質問）は既存で足りるが、consult 画面のルートパラメータは `{ id }` のみで、失敗種のプレフィルや写真の引き継ぎには**画面側の小拡張が要る**。
- **判断**: 対応する。注記を追加。

### 4. 「移行 zip を渡すと GPS が出る」を無条件に書いていた

- **状態**: done
- **重大度**: 中
- **影響**: リスクを過大に見せていた
- **指摘**: 通常経路の写真は保存時の JPEG 再エンコードで EXIF が落ちている（expo-image-manipulator の既知動作・expo/expo#28913）。GPS が出るのは**圧縮フォールバックで原本のまま保存された写真が混ざっている場合に限る**。
- **判断**: 対応する。条件付きに書き直し、根本対処がフォールバック側であることを明記。

### 5. 楽しみ代の金額が文書（¥300/月）とモック（¥50/月）で不一致

- **重大度**: 低
- **指摘**: モックは「赤字 ¥300 ÷ 6 か月 = ¥50/月」で自己整合しており、文書側に算出規則が無かった。
- **判断**: 対応する。文書に算出規則を追記。

### 9. プラットフォーム説明の HEIC の言い方

- **状態**: wontfix
- **重大度**: 低
- **影響**: チャット上の説明のみで、文書には書いていないため修正対象なし
- **指摘**: 「iPhone の既定は HEIC」は経路依存 — `launchImageLibraryAsync` は既定（quality 1.0・representationMode 'current'）で HEIC 資産を無変換で返すが、`launchCameraAsync` は常に JPEG 再エンコード。また通常は保存時に JPEG 化されるので、HEIC が残るのはフォールバック時のみ。
- **判断**: 文書化する際（Issue 本文）にこの精度で書く。既存文書に該当記述は無いため修正対象なし。

## 確認できた正しい主張（Issue 化の根拠）

- 週次自動バックアップは JSON のみで写真を含まない（`backup.service.ts:978-979`）
- 移行 zip は欠落写真の `local_path` を null 化 → `photos.local_path` は NOT NULL → 復元の INSERT が制約違反 → **トランザクションごと ROLLBACK して復元全体が失敗**（帰結まで実装どおり）
- `restoreLocalBackup`（JSON 復元）はパスを書き換えない（絶対パス保存 × iOS のコンテナ UUID 変化で全写真が失われる）
- `deletePlanting` は photos 行だけ消しファイルを残す。`cover_photo_path` のファイル削除処理はリポジトリに存在しない（更新時の旧ファイルも残る）
- 圧縮フォールバックで原本コピー → EXIF/GPS 残留（`photo-storage.service.ts:66-79, 242-243`。圧縮成功時に EXIF が落ちるのは expo/expo#28913 で裏取り）
- `AndroidManifest.xml:16` は `allowBackup="true"` で `fullBackupContent`/`dataExtractionRules` 指定なし

## 実機確認（AQUOS SH-RM19s / Android 13・2026-08-26）

修正 3 コミット（`44bd8cd` / `650874b` / `26c7acb`）を**アップグレードインストール**して確認した。
署名が一致したので、データ消去も再インストールもせず、**実データを保ったまま**検証できた。

| 確認                                  | 結果                                                                                                   |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| アップグレードでデータ保持            | ✅ 栽培 3 件・リマインダー・収穫 4 件が健在。migrate v13 がエラーなく完走                              |
| **記録機能**（写真つき作業ログ 3 件） | ✅ 保存され、一覧・詳細にサムネイルが出る（相対保存 → 解決の往復が実機で成立）                         |
| **編集で写真が消えないか**            | ✅ 写真を触らずメモだけ変更して保存 → **写真は残った**。`replacePhotos` の正規化が実データで効いている |
| **成長記録**                          | ✅ 21 日目（種まき直後の土）× 53 日目（茂った株）が並び「この間 32 日」。選び直しの帯も動く            |
| クラッシュ                            | ✅ 一連の操作で 0 件                                                                                   |

**この端末の既存データには写真が 1 枚も無かった**ため、v13 の「絶対 → 相対」変換そのものは
実データでは検証できていない（変換対象が無かった）。そこは実 SQLite のテスト
（`schema-sql.test.ts` の v13 節: 絶対→相対・冪等・NULL・知らない場所は切り詰めない）で担保する。

**副産物: 提供写真の EXIF** — 検証用に提供された写真 13 枚は**すべて EXIF に GPS 座標（緯度・経度・標高）を持っていた**。
ストア掲載物・サンプルデータへ入れる場合は再エンコードによる EXIF 除去が必須
（`sanitize-user-media` Skill の手順）。アプリ内へ取り込むぶんには保存時に
JPEG 再エンコードされるので残らない（本ブランチで fail closed 化した経路）。
