# 検討: ホームに「1 か月グラフ」を置けるか（2026-08-24）

> 発端: 「生理周期管理アプリのように、ホームに 1 か月のグラフ・気温のグラフ・
> 〇〇日の凡例があると、すごく AI 駆動に見えた」というユーザー提案。
> **実現性**と**何を出すべきか**を調べた記録。実装はまだしていない。
>
> 関連: R20（天気連携）= WBS 4.13 / R33（定植適期通知）/ 既存の R10「つぎの作業」

---

## 0. 結論（3 行）

- **「直近 1 か月の実測気温グラフ」はいま出せない。** 位置が決まらない・無料 API が使えない・
  法（気象業務法）に触れる・カレンダー画面と重複する、の 4 つが独立に効く
- **形を変えれば出せて、しかも費用ゼロ。** 「栽培ごとの**進行帯**（植え付け→収穫適期）＋
  平年気温の背景＋**今日のひとこと**」なら、端末内データと同梱の平年値だけで完結する
- **「AI っぽさ」の正体はグラフではない。** 体感を作っているのは
  **自分の入力を名指しする説明文**で、寄与はおよそ「説明文 7 : 言い切り 2 : 予測精度 1」

---

## 1. できないこと（そのままの形では）

### 1-1. どこの気温か決まらない

アプリが持つ位置情報は**寒冷地 / 中間地 / 暖地の 3 区分だけ**（`region.service.ts:13-31`）。
緯度経度は端末にもスキーマにも無く、`expo-location` も入っていない。

一方、気温データ源はすべて地点指定を要求する（Open-Meteo・OpenWeatherMap は lat/lon 必須、
気象庁は観測所コード）。3 区分から気温を出すには「暖地＝福岡」のように代表地点を
決め打ちするしかないが、それは**位置の捏造**になる。

**帯の中のばらつきが、帯の間の差より大きい。** 寒冷地の定義は「北海道・東北・標高の高い地域」で、
旭川と福島の平地では 10℃ 違う。暖地も那覇と福岡で 5〜6℃ 開き、これは
東京（中間地）と福岡（暖地）の差 1〜2℃ を優に超える。**1 本の線を引いた瞬間に嘘になる。**

### 1-2. 無料で使える API が無い

| 候補           | 判定 | 理由                                                                                                                                                                                                                                        |
| -------------- | ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Open-Meteo     | ❌   | 規約が「**広告を表示するアプリ**」を商用と定義。AdMob 入りの本アプリは無料枠の対象外。商用は $29/月〜（WBS 4.13 の 2026-08-17 実測記録にあるのは**規約条件のみ**。価格は open-meteo.com/en/pricing の 2026-08-24 時点・通貨表記は要再確認） |
| 気象庁         | △    | 無料・商用可・出典 1 行のみ。ただし**地点別 JSON の保持は約 10 日**（実測: 8/16 は 200、8/15 は 404）。過去 30 日は `daily_s1.php` の HTML スクレイプが要る                                                                                 |
| OpenWeatherMap | ❌   | 過去 30 日 = 30 コール、カード登録必須、CC BY-SA のシェアアライク＋ロゴ表示義務                                                                                                                                                             |

気象庁を使う場合、**日 1 回のスクレイプ＋キャッシュを持つサーバー実装**になる。
実稼働サーバーはこのリポジトリではなく**だいどこ側**（本リポジトリの `apps/server` は
`/garden` を持たない死んだコピー・#150）なので、必ず 2 リポジトリ跨ぎの作業になる。

### 1-3. 「今夜は霜注意」は許可なしに出せない

気象業務法第 17 条。気象庁以外が予報業務を行うには長官の許可が要る。
**過去の観測値の表示は予報ではないので対象外**だが、最低気温から「今夜霜が降りる」を
導いて出すのは独自予報にあたる（2026 年 5 月末施行の改正で無許可事業者の名前公表制度が追加）。

これは既に自分たちで結論を出している — `docs/WBS.md:198-202`:
「霜も**注意報を伝えるのが本筋**で、最低気温からの推定は補助に留める」。
**出せるのは「◯◯市に霜注意報が出ています（出典: 気象庁）」の転送だけ。**

### 1-4. 「1 か月の作業・収穫グラフ」はカレンダーと重複し、しかも一度却下している

`app/calendar.tsx` は既に月頭〜月末を `getTimeline({from,to})` で引き、
日ごとに「作業=緑ドット / 収穫=橙ドット」を出している。**1 か月ぶんの同じデータを
同じクエリで日別に可視化した図そのもの**。

さらに `calendar.tsx:7-10` と `utils/gardenCalendar.ts:12-15` に記録が残っている（以下は要旨）:
「作業種別ごとに 6 色を割り当てる案もあったが、1 マスが 40px 前後しかなく色を増やすと
判別できない／件数を点の数で表す案も凡例と衝突して読めなくなった（**実機で確認**）」。

**収穫量の軸も成立しない。** `quantity` は任意入力が仕様（写真だけの収穫が成立・R06）で、
`harvest.service.ts:161-179` が「『個』と『g』を足せないので 1 つの数にはまとめられない」と
明文化している。日別の収穫量折れ線は、欠測だらけか単位混在のどちらかになる。

## 2. できること（費用ゼロ・ネットワーク不要）

### 2-1. 気温は「同梱の平年値」で足りる

気象庁の平年値（1991-2020）を地域帯ごとの代表地点ぶん**コードに同梱**し、
月平均を線形補間して日別の目安を出す。`crop-master.ts` と同じ経路（出典を明記した定数）。

- ネットワーク・課金・位置情報のいずれも増えない
- オフラインで動く（非機能要件「記録系はオフラインで動作」を守れる）
- ラベルは必ず「**平年の気温**」。実測と偽らない
- 出典表記: 「出典: 気象庁ホームページ（URL）」、加工したら「〜を加工して作成」

先行例がある（Mahiro Apps の収穫日カウントダウンが平年値 10 都市ぶんを埋め込んで
線形補間している）。**実測気温を後から任意入力できるようにすれば、
平年値ベース → 実測補正、という精度向上の階段になる。**

### 2-2. 描画基盤は既にある

`react-native-svg 15.12.1` は直接依存として入っており、審査提出済みの AAB にも
`libreact_codegen_rnsvg.so` が同梱されている（autolink 対象 7 件のひとつ）。
**ネイティブ依存の追加も prebuild も要らない。**

ただし条件つき: **react-native-svg のプリミティブ直書き（＋必要なら純 JS の d3-scale/d3-shape）
以外は採らない**。チャートライブラリを入れるとネイティブが増える可能性があり、
CLAUDE.md §4 の「アニメーションのネイティブ依存は持っていない」方針と衝突する。

## 3. 何を出すか — 周期アプリからの転用

### 3-1. 「AI っぽく見える」の正体

調べた結果、体感を作っているのは**予測の精度ではない**。

| 要素                 | 寄与（仮説） | 中身                                                                                           |
| -------------------- | -----------: | ---------------------------------------------------------------------------------------------- |
| **説明文（名指し）** |            7 | 「3 日前に追肥しましたね」のように**自分の入力を引用**する。中身はルールベースの出し分けでよい |
| **言い切り**         |            2 | 「あと 5 日」。範囲（3〜7 日）を出すと解釈が利用者に戻り「で、どうすれば」が残る               |
| 予測の精度           |            1 | 平均値の足し算で足りる。上げても体感はほとんど動かない                                         |

CHI 2023 の研究では、**まったく同じ一般的な文章**でも「あなた向けに作られた」と信じて
読むと評価が上がり、一般的な記述として提示されると下がる。つまり AI っぽさは
**参照の可視性**であって、推論の質ではない。

### 3-2. 円ではなく横帯にする（最重要の設計判断）

周期アプリが円（リング）を使うのは、月経が**周期的に回帰する**から。
**播種→収穫は一方向の進行で回帰しない**ので、円だと「どこが始まりでどこが終わりか」が読めなくなる。

- **栽培 1 本 = 横帯**（左＝植え付け日、右＝収穫適期の終わり、現在位置に today マーカー）
- **円は別レイヤーに回す** — 1 年の作付けサイクル（春まき・夏の管理・秋冬まき・冬の土づくり）。
  ここは既存の「今月の菜園仕事」＋地域設定が材料になる
- **2 つの時間軸を 1 つの図に混ぜない**

### 3-3. 対応表

| 周期アプリ            | さいえん手帳                                     |
| --------------------- | ------------------------------------------------ |
| 周期の何日目          | 植え付けからの**積算温度**（当面は経過日数）     |
| 生理予定日            | 収穫適期の開始日                                 |
| 妊娠可能期の帯        | **収穫適期の帯**（採り始め〜採り終わり）         |
| 排卵日（点線の丸）    | 収穫のピーク日                                   |
| 遅れ（グレー）        | 判定不能（記録が無い・気温が読めない）           |
| 「排卵まであと N 日」 | 「収穫まであと N 日」                            |
| 症状ログ              | 作業ログ（水やり・追肥・写真）                   |
| 今日の insights       | **今日のひとこと**（直近ログと生育段階を名指し） |

**帯は菜園のほうが嘘が少ない。** 生理予測の帯は本来「誤差」だが、収穫適期の帯は
実際に幅のある現象（採り始めから採り終わりまで）なので、帯表示に無理がない。
さらに菜園固有の強みとして**帯の終わり（採り遅れ）**が意味を持つ —
周期アプリに対応物が無い情報で、「あと N 日で採り時が終わります」は言い切りとして極めて強い。

### 3-4. 日数ではなく積算温度（GDD）が本命

周期アプリの「周期 N 日目」が効くのは、それが進行度と相関するから。
**菜園で経過日数を同じ位置に置くと、猛暑年・冷夏年でズレて「外れるアプリ」になる。**

植物の進行を駆動するのは日数ではなく受けた熱量の合計（積算温度）。
トマトは開花後 1,000〜1,100℃、サツマイモは植付から 2,900〜3,300℃ といった目標値がある。
**気温を入れた瞬間に、予測は「マスターの固定値」から「あなたの畑の今年」に変わる** —
これが個別化の本体。

ただし**作物マスターに温度の情報は 1 つも無い**（`CropCalendarWindow` は region/kind/月のみ、
`CropGuideMaster` も日数ベース。`適温|積算温|℃|GDD` で grep して 0 ヒット）。
GDD をやるなら**作物ごとの目標値を出典つきで書き足す**新規データ投入が要る（30 作物）。

## 4. レイアウト案

現行ホームは 6 ブロック（読み取り待ち → 今日のリマインダー → つぎの作業 → 育てているもの →
今月の菜園仕事 → さいきんの記録）で、**「自分で決めた予定のほうが確度が高いので提案より上」**
という序列の根拠がコメントに明記されている。**大きな図を最上段に置くとこの原則を破る。**

### 案 A（推奨）: 「育てているもの」を進行帯カードに格上げする

新しいブロックを足さず、既にある横スクロール帯を作り替える。**栽培が複数ある以上、
単一の巨大リングは最初から成立しない**（周期アプリは常に 1 周期 1 本）。

```
┌─ 育てているもの ────────────────────────┐
│ ┌──────────────────┐ ┌─────────────────┐ │
│ │ 🍅 トマト  アイコ  │ │ 🥒 キュウリ      │ │
│ │ 収穫まで あと 12 日 │ │ 追肥まで あと 3 日│ │  ← 言い切り・主語は自動で切替
│ │ ▓▓▓▓▓▓▓▓░░▚▚▚▚▚▚  │ │ ▓▓▓▓░░░░░░░░░░░ │ │  ← 塗り=済み / ░=これから / ▚=収穫適期の帯
│ │ ・  ・   ・ ▲      │ │ ・    ▲          │ │  ← ドット=作業ログ / ▲=今日
│ │ 植付7/8    45日目   │ │ 8/1      12日目  │ │
│ └──────────────────┘ └─────────────────┘ │
└───────────────────────────────────────┘
```

- **今日の位置は 3 重に冗長化**（帯上の ▲ ／ 「45 日目」の数字 ／ カウントダウン）。
  周期アプリが「見失っていない」感覚を作っている仕掛けをそのまま借りる
- **確信度は線種で二値**に符号化する（塗り＝記録済みの過去 ／ 縞＝これから来る適期）。
  確率や % は出さない
- **カウントダウンの主語は自動で切り替える** — 植え付け直後は「追肥まであと N 日」、
  追肥済みなら「収穫まであと N 日」、収穫開始後は「**採り時の終わりまであと N 日**」
- **凡例パネルは置かない。** 帯の上に「収穫適期」と直接ラベルを置く。
  **ホームで凡例が要る色分けは、その時点で複雑すぎる**（実機で却下した経緯とも一致）
- 色は 3〜4 色まで、強度ではなく**状態**を指す。生育中＝若葉の緑／適期＝暖色／
  判定不能＝グレー（「失敗」ではなく「情報不足」の意味に割り当てる）

### 案 B: 気温は「帯の背景」に薄く敷く

独立した気温グラフを置かず、進行帯の背後に平年気温の薄い折れ線を敷く。
**気温は主役ではなく、帯がなぜそこにあるかの説明**として働く。

「平年の気温」ラベルと出典を必ず添える。実測が取れるようになったら
（＝ WBS 4.13 で市区町村選択が入ったら）同じ場所を実測に差し替えられる。

### 案 C: 「今日のひとこと」を 1 行足す

**費用ゼロで体感がいちばん動く箇所。** 直近の作業ログと生育段階を名指しする 1 行。

> 3 日前に追肥しましたね。いま 45 日目、収穫適期まであと 12 日です。

出し分けはルールベースで足りる。**有効期限は 1 日**（残り続けると「貼ってあるだけ」に劣化する）。
既存の `describeNextAction` が既に「**断定を主文にし、括弧内に根拠を必ず添える**」形
（例: 「収穫適期に入りました（目安 約 45 日・いま 50 日目）」）になっているので、
新規発明ではなく**この型をホーム全体へ広げるだけ**。

### 却下: 1 か月の気温・作業・収穫グラフをホームに置く

§1-1〜1-4 の 4 点。カレンダー画面と重複し、数量軸が成立せず、気温は嘘になり、法にも触れる。

## 5. コスト影響（cost-impact）

| 案                                        | 1 回あたり     | 1 人あたり / 月 | サーバー側の天井 / 月                                                  |
| ----------------------------------------- | -------------- | --------------- | ---------------------------------------------------------------------- |
| **案 A/B/C（同梱平年値・端末内集計）**    | **¥0**         | **¥0**          | **¥0**（サーバーを一切使わない）                                       |
| 実測気温（気象庁スクレイプ + キャッシュ） | ¥0（推論なし） | ¥0              | Railway 共用のため**固定費の増分なし**。ただし運用工数と障害面が増える |
| Open-Meteo 商用                           | —              | —               | **$29/月（約 ¥4,400）** — 現状の推論天井 ¥2,100/月 の 2 倍             |

**固定費は案 A/B/C で増減なし。** 変動費も増えない（Gemini を呼ばない）。
`docs/インフラ・NW構成設計.md` §5 の数字は動かない。

実測気温をやるなら、Open-Meteo 商用は**推論費より高くつく**ので採らない。
気象庁スクレイプは費用ゼロだが、**だいどこ側 Railway に新しい面積を足す**ことになり、
「サーバーの面積を増やさないことが最大のコスト削減策」（§1-1）と正面から当たる。

## 6. 引き受けるリスク

**断定のトーンは、外れたときの自己否定と同じ設計から出てくる。**

周期アプリでは、28 日周期の女性のうち 14 日目に排卵するのは 1 割程度なのに、
多くのアプリが誤差を説明せず 14〜15 日目を表示する。予測が外れたとき利用者は
「アプリが外れた」ではなく「**自分がおかしいのでは**」と受け取る（Epstein らの CHI 2017）。

菜園に転用すると「天気のせい」ではなく「**自分の育て方が下手**」になる。緩和策:

1. 帯を出すときは必ず「目安」の根拠を小さく併記する（既存 `describeNextAction` が既にやっている）
2. **外れた側にも言葉を用意する** —「まだのようです。今年は 7 月の気温が低めでした」のように
   **原因を外部に置いた説明文**を出す
3. 予測が外れることを異常ではなく既定として扱う。`crop-master.ts` のコメントが既に
   「一般的な露地・プランター栽培の目安。品種や年ごとの気候では前後する」と書いており、
   UI 文言もこの姿勢に揃える

## 7. 進め方の案

いまは **1.2 の機能追加中**なので、着手はその後。

| 段    | 内容                                                            |     費用 | 依存                                            |
| ----- | --------------------------------------------------------------- | -------: | ----------------------------------------------- |
| **1** | **今日のひとこと**（案 C）— 直近ログを名指しする 1 行           |       ¥0 | なし。既存サービスだけで書ける                  |
| **2** | **進行帯**（案 A）— 「育てているもの」を帯＋カウントダウンに    |       ¥0 | react-native-svg（導入済み）                    |
| **3** | 平年気温を同梱（案 B）— 帯の背景と「平年より暑い/寒い」の説明文 |       ¥0 | 気象庁平年値の書き起こし（出典明記）            |
| **4** | GDD 化 — 作物ごとの積算温度目標を 30 作物ぶん書き足す           |       ¥0 | 出典調査（`docs/栽培暦の出典.md` と同じ手続き） |
| **5** | 実測気温（R20 / WBS 4.13）— 市区町村選択 + 気象庁キャッシュ     | 運用工数 | 2 リポジトリ跨ぎ・データセーフティ再確認        |

**1 と 2 だけで体感の 9 割**（説明文 7 ＋ 言い切り 2）が取れる、というのが調査の結論。
気温（3〜5）は精度の話であって、体感の話ではない。
