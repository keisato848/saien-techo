## 1. 追加する 4 機能

いまのアプリは「ユーザーが書きに来る手帳」で、書くことが尽きる 3 週目に開かれなくなり、
シーズンが終わると開く理由が消える。この 4 機能は**記録 → 予測 → 結果 → 翌年**を閉じる。

### 機能 1: 週次リスクチェック（1.3）

**作物 × 経過日数 × 月 × 地域**から「今週この作物に起きやすい失敗」を 1 件だけ提示し、
2 タップで済む点検を促す。

- 通知は**週 1 回・最上位 1 件のみ**。閾値未満の週は通知せず、ホームに「今週は要注意なし」と表示
- 「見た → 兆候なし / 兆候あり」の 2 択。**どちらも作業ログ**（新種別 `check`）に記録される
- 兆候ありは対処 1 手を提示し、既存の AI 相談へ写真つきで送れる（新規エンドポイントなし。
  ただし consult 画面のルートパラメータは現状 `{ id }` のみ — 失敗種の質問文プレフィルや
  写真の引き継ぎには**画面側の小拡張が要る**）
- **誤警告の抑制**: 同一の失敗種で「兆候なし」が 2 回続いたら重みを半減（`next-action` の
  snooze と同型の `app_meta` 辞書）。使うほど通知が減る
- データ源は**新規の失敗マスター**（作物 × 失敗 × 発生月 × 地域 × 対処）。
  出典は病害虫防除所・農水省で、栽培暦 30 作物と同じ出典明記のレールに乗せる

> **気象業務法への配慮**: 独自の気象予測は出さない。提示するのは「〜が出やすい時期です」
> という**確認依頼**で、根拠は月窓 × 地域 3 区分のみ。天気そのものは R20（4.13）で
> 気象庁の注意報を転送する形に委ねる。

### 機能 2: 収支の可視化（1.5）

支出（資材・買い物リスト）と収穫を**円**で突き合わせ、回収率を出す。

- **支出入力**: 買い物リストのチェック時に「¥いくら？」を任意で 1 タップ入力。
  `materials` / `garden_shopping_items` に `price` を追加。**道具は初期投資として分離**
  （クワ ¥3,000 が初年度を赤字に見せて挫くのを防ぐ）
- **収穫の金額換算**: 既存の写真読み取り（1.2）が返す `count` に市価マスターを掛けるだけ。
  **新規推論ゼロ・後処理 1 行**
- **市価マスター**: 総務省・小売物価統計（e-Stat）と農水省・食品価格動向から静的同梱。
  表示は常に「目安 ¥◯（出典: 〜）」で、**タップで自己申告値に上書き可**。
  統計に単価が無い作物・単位は「換算対象外」と正直に表示する
- **「個と g を足せない」制約の解**: 単位換算はしない。
  `(トマト, kg)=¥700/kg`、`(キュウリ, 本)=¥60/本` と**行ごとに円へ直し、円だけを合算**する。
  円が唯一の共通単位。換算できなかった収穫は「¥換算 12/15 回」と欠測を明示
- 表示は**獲得フレームのみ**: 「あと ¥540 で黒字」「元が取れました（支出 ¥1,980・62 日目）」。
  支出を催促する通知は出さない（請求書化の回避）

### 機能 3: 実績による予測補正（1.4）

作物マスターの固定日数を、その人の実績で上書きしていく。

- 栽培完了時に `predictedDays` / `actualDays` を保存し、**作物 × 場所**ごとに補正係数を学習
  （直近年・同季節を重く加重、**±30% にクリップ**）
- 表示は必ず出自つき: 「目安 45 日 → **うちは 52 日**（去年 2 回の実績から）」。
  信頼度 3 段階（一般値 / 参考 / 実績値）で、記録が増えると表示が格上げされる
- **初収穫の瞬間に答え合わせカード**: 「目安 45 日 → 実際 52 日。実績に反映しました」。
  外れの原因は**常に外部へ帰属**するテンプレ（「植え付けが例年より遅く、
  気温が下がる時期にかかった影響とみられます」）。外れ＝データが増えたイベントとして扱う
- **GDD（積算温度）は採らない**: `harvestAfterDays` は基準温度が不明なので、
  そこからの温度換算は根拠のない較正になる。1 年目＝マスター値、2 年目＝実績値の二段で足りる

### 機能 4: 締めくくり記録と翌年への引き継ぎ（1.4 → 1.6）

- **片づけレビュー（30 秒）**: 撤収時にカルテを自動生成し、「また育てる？（また / 改良して / やめる）」
  ＋「来年の自分にひとこと（任意 1 行）」を預かる。適期超過＋ログ途絶で自動プロンプト
- **シーズン集計**: 作物別損益、無事だった週数、出た失敗、`¥換算 N/M 回`。
  赤字作物には「楽しみ代」の別フレームを併置し、突きつけて終わらせない
  （算出は赤字額の月割り。例: 赤字 ¥300 ÷ 6 か月 = ¥50/月）
- **翌年の再生（1.6）**: 去年「兆候あり」だった週 ±2 週 × 同科 / 同じ場所の警告を
  マスター警告より強く出し、**そのとき書いたひとことを一緒に返す**。
  集計結果は作付け計画（4.7）の下書きへ流す

## 2. ループの閉じ方

```
記録 ──────────→ 予測 ──────────→ 結果 ──────────→ 翌年 ──┐
週次チェック       実績日数         答え合わせ        個人化警告  │
収穫（写真）       回収見込み       黒字化           引き継ぎメモ │
支出（1 タップ）                    シーズン集計      作付け下書き │
  ↑                                                            │
  └────────────────────────────────────────────────────────────┘
```

各辺が次の辺の入力になっている。既存の**「何も使わない」（記憶＋写真フォルダ）には
構造上できない**のは 3 つ: 先回りして知らせる / 元が取れたか答える / 去年の記述を該当時期に返す。

**3 週間で飽きる問題への対応:** 飽きは「書くことが尽きる」×「見返す理由がない」で起きる。
週次チェックが**書くネタを供給**し、守り（点検の記録）と攻め（回収メーター）の
2 系統の見返りが空白期・収穫期のどちらでも途切れない。

### 6-1. 見比べの却下理由を訂正する（2026-08-24・実装で再検証）

当初「バックアップ肥大」「毎日撮る習慣が 3 週間で切れる」を却下理由に挙げたが、
**実装を読み直したところ 2 つとも成立しない。** 訂正する。

| 当初の却下理由                | 判定         | 実装が示すこと                                                                                                                                                                                                                                                                                                                                                        |
| ----------------------------- | ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| バックアップが肥大する        | **誤り**     | 週次の自動バックアップは **JSON だけで写真を含まない**（`backup.service.ts:975-979`「写真は含めない…週ごとに複製すると容量だけが増えていく」、UI にも「写真は含みません。」）。写真の実バイトが入るのは**機種変更用の移行 zip だけ**で、しかもその問題は base64 のオンメモリ一括処理という実装欠陥（`backup.service.ts:749-796`）であって、見比べ機能とは独立に直せる |
| 毎日撮る習慣が 3 週間で切れる | **根拠なし** | **撮影を促す通知は 1 つも実装されていない**（`notification.service` / `reminder.service` / `next-action.service` に写真の参照 0 件）。計測手段も無く（analytics 依存なし）、「3 週間」は `ペルソナ・競合分析.md:37` に**未検証の仮説**と明記されている。しかも本書 §0 で継続 9.0（全案中最高）を与えながら習慣を理由に落とすのは矛盾していた                          |
| AI の説明文が価値の本体       | **誤り**     | R16 は「**AI は介在しない**」と要件定義に明文化されている（`要件定義.md:236`）。AI 説明文は R32 の上乗せで、依存の向きは R32 → R16。**見比べ UI は AI 無しで完結する定義**                                                                                                                                                                                            |

**したがって「2 枚を並べて見る」（R16 / WBS 4.4）は AI を使わず変動費 ¥0 で成立する。**

#### ただし本当の律速は写真基盤にある

費用でも習慣でもなく、**写真まわりの実装が比較に耐えない**のが実際の障害だった。

1. **欠損の検知が存在しない。** `onError` はアプリ全体で 0 件、`expo-image` も未導入。
   プレースホルダ分岐は `photoUri ? <Image/> : <placeholder/>` で **URI が null かどうかしか見ない**ので、
   「DB に行はあるがファイルが無い」状態には反応せず、栽培詳細では 200px の空白が出る
   （`plantings/[id].tsx:172-174`）。**「削除されていたら別の写真を選ぶ / 無効化する」という
   処理は妥当だが、その土台がまだ無い**（新規に作る対象であって、既にある前提にはできない）
2. **移行 zip に整合性バグがある。** 書き出しは欠落写真の `local_path` を null にするのに
   （`backup.service.ts:764-768`）、`photos.local_path` は **NOT NULL**（`migrate.ts:266`）
3. **孤児ファイルが残る。** `deletePlanting` は photos 行を消すがファイルを消さない
   （`planting.service.ts:352-397` に `deleteGardenPhotoFiles` の呼び出しが無い）。
   個別の作業ログ削除では消えるのに、親ごと消すと残る非対称
4. **定点性の担保が無い。** `定点` / `ゴースト` の実装は 0 件。角度も距離も揃わない 2 枚を
   重ねても「成長の比較」にならない。R32 は依存に「R16 の**定点撮影 UI**」を挙げている
5. **撮影日そのものの列が無い。** `photos` は 8 列で、EXIF の撮影日時を持たない（`created_at` はあるが**保存時刻**で、ギャラリーから選んだ写真では撮影時刻と一致しない）
   （実務上は所有者側の `logged_at` / `harvested_at` で代用できるが、
   写真だけを時系列に並べる画面では前提を確認すること）

**⚠ 個人情報の経路（見比べとは独立に対処が要る）**: 圧縮に失敗すると**原本をそのままコピー**する
フォールバックがあり（`photo-storage.service.ts:66-78, 243-244`）、その場合 **EXIF の GPS 座標が
端末内に残る**。移行 zip は保存済みファイルの生バイトをそのまま格納するので、**フォールバックで原本のまま保存された
写真が混ざっている場合に限り**、書き出したファイルを外部へ渡すと位置情報が出る
（通常経路の写真は保存時の JPEG 再エンコードで EXIF が落ちている — expo/expo#28913 で確認）。
根本対処は zip 側ではなく**フォールバック側**（原本コピー前に EXIF 除去、または保存を拒否）。
DoD 3（個人情報の非公開確認）の観点で、比較機能より優先度が高い。

#### 修正した進め方
